# PayBack stability repair plan

Status: draft v2, awaiting independent review. No production implementation begins until approved.
Baseline: commit `4fa2bedecaf14c1079a4eef631c4842557036c6a`; 29 grouped findings and 152 scenario classes in `baseline.json`.

## Safety facts and scope

1. Neither linking nor cleanup may change historical total liability or revive/forgive settled debt. Canonical account IDs remain immutable; only consent-bound server operations establish global alias provenance. Owner-local merges cannot alter another owner's financial content.
2. Every async mutation stays bound to its starting actor. New storage/wire fields are optional on existing documents, validators and Swift DTOs evolve together, and old-client writes cannot erase server-owned identity, revocation, currency or completion state.

Implement all code-remediable findings F01–F29, including supporting compatibility and tests. Do not invent a historical currency, rotate live Clerk identity infrastructure, repair production records, or flip migration readiness markers. External operational requirements must be explicitly tracked rather than labeled fixed. This PR can prepare production auth configuration and enforce release readiness; actual provider setup/account continuity requires operator action and must not silently strand current accounts.

### 2. Identity, provenance and financial-history preservation (F02–F05, F10, F24)

- Remove normal hydration/import/name-only identity inference. Use authenticated canonical/alias equivalence; preserve distinct same-name UUIDs. Manual add reuses a historical identity only when truly unambiguous before display projection, otherwise creates a distinct candidate or requires selection.
- Preserve original money-bearing split rows, stable split IDs, amounts and settlement flags in the V3 identity path. Establish aliases without physically collapsing financial rows. Every matching raw canonical/alias row contributes to a person's total; settled means all applicable rows are settled. Update `Expense.split/isSettled`, detail selectors, settlement selection and realtime acknowledgement to aggregate all matching rows, independent of ordering. Settlement-by-member explicitly marks all authorized matching rows settled/unsettled; it is not reversal of a payment transaction. A batch containing different currencies is prohibited. Old structural upserts may not remove, reclassify or change protected historical rows.
- Keep physical coalescing only in existing synchronous compatibility paths when settlement state is uniform. A mixed-state collision fails atomically before any alias/friend/financial writes with an actionable message; do not introduce duplicate same-member split rows into old contracts. V3 alias-only merging is the complete successful path for mixed-state histories, guarded by financial capability 2 as specified below.
- Legacy accounts missing member_id receive a new server-generated canonical UUID during users:store before the authenticated account snapshot is returned, so existing clients that hydrate that account skip client bootstrap. A versioned bootstrap response also returns the assigned UUID for explicit current-client recovery. Concurrent/retried calls return the same assigned canonical. The old client-chosen bootstrap endpoint is idempotent only for an exact existing canonical match; an arbitrary/mismatched requested placeholder rejects with refresh/upgrade-required rather than returning false success. A stale legacy caller may have to refresh; it must never continue under a client-requested wrong UUID. Already assigned canonical IDs remain immutable. New clients adopt the response before any dependent writes. Historical claims require consent-bound linking.
- Implement the concrete indexed job protocol in section 6 for both global claim visibility and owner-local merging. Reference presence never proves authority. Foreign financial content stays byte-for-byte unchanged; derived visibility/revisions may change only from live consent, participant status and suppression rules.

### 3. Request and invitation lifecycle (F01, F14–F15, F23, F26–F27)

- Fresh signup preserves live, unexpired incoming email requests bound to a valid active requester and owned target, across both cleanup paths. Deleted-account artifacts still clean up safely.
- Decline/cancel only act on pending requests. Accepted evidence remains durable. Repeating legacy send preserves confirmed status.
- Invite creation recovers an existing active token for the same owned unlinked friend. Client builds its URL from the returned canonical token ID. Different payload/owner collisions still reject; explicit revoke remains owner-only.
- Add optional owner-validated merge selection to email acceptance, matching V3 invite claim semantics in section 6. iOS offers selection before accept; no name-based automatic merge. Store accepting account, selected member ID and operation ID as durable evidence. Same claimant/selection replay returns the original completed or pending result; different claimant/selection rejects. Compatibility requests keep their original return shape and only replay completed operations. Lost-response recovery and process relaunch resume the stored operation.
- Friend-add UI updates confirmed state only after persistence succeeds. Failed request creation may retain an already persisted manual friend; failed friend persistence may not.
- Use paginated incoming/outgoing request APIs in iOS; keep compatibility endpoints for old clients. Preview must not present inaccessible pre-link history as a proven zero balance.

### 4. Expense authorization, money and direct ledgers (F06–F07, F20–F22, F28–F29)

- One canonical participant authorization path for all expense contexts and updates: payer belongs to the involved identity set; participant, involved and split identity sets agree; identities are authorized by current group membership or confirmed direct/grouped-individual friendship. Derive linked accounts/emails from trusted member/link provenance, never arbitrary input email. Existing owner metadata edits with unchanged historical participants remain allowed after friendship removal. Inactive historical participants and settled amounts cannot gain new exposure through a metadata edit.
- Self derives from authenticated canonical equivalence, never persisted creator-relative is_current_user. Require confirmed friendship for every genuinely new direct expense in both directions.
- Add compatible `expenses:createV2` returning the persisted expense and selected ledger identity. Keep `expenses:create`'s original document-ID return. A normalized canonical pair mapping/index chooses one authorized ledger transactionally; among eligible legacy duplicates choose deterministically by stable creation time/document ID, retaining all legacy financial records. Validate membership/owner consistency before reuse. Concurrent first saves converge through the indexed pair row. Alias transitions re-resolve the pair; do not globally fuse unrelated owner-local identities. The current iOS service returns the canonical saved expense/group before AppStore commits its draft; old stale drafts do not create duplicate ledgers and converge on hydration. Retry by expense ID preserves the original selected ledger and rejects changed immutable context.
- Shared money validation has three modes. **Authoring:** explicit USD, finite positive total <= 1,000,000,000 USD, nonnegative shares/subexpenses, integer cents <= 100,000,000,000, exact cent conservation of shares, no refunds/negative debt. **Existing metadata/settlement:** unchanged finite historical total/shares/currency may retain fractional precision; total-only or currency-only changes cannot sneak through metadata updates. **Historical restore:** preserve finite nonnegative supported legacy precision and stable rows, require finite/conserved total within documented floating representation tolerance, reject malformed/inconsistent input with an explicit row error; never invent a missing payer split. All public create/update/import paths select the appropriate shared validator. Legacy new creates lacking currency reject upgrade-required; existing omitted fields preserve stored data.
- Extract production minor-unit split allocation for equal/percent/shares/manual/itemized modes. Sort remainder allocation by stable normalized member UUID, never incidental array order. Convert the bounded total to cents once, allocate floors then deterministic remainders; verify the sum. Adjustments must sum to zero and cannot make a share negative. UI disables save with a clear reason; server enforces equivalent rules. Tests must exercise the real production function and its exact mutation payload.
- **Currency policy:** new interactive authoring is explicitly USD only; remove unsupported crypto/conversion UI. Persist optional immutable `currency_code` in expense schema, Swift model/DTOs and backups. Decoder/import explicitly preserve nil; only a new-authoring initializer defaults USD. Imported explicit supported ISO codes (including EUR) stay intact. Omitted update currency preserves existing code or nil; supplied conflicts reject. Known denominations aggregate separately. Unknown records remain individually inspectable and are never summed into an 'unknown currency' balance. USD dashboards never include EUR/unknown. Currency-aware summaries cover activity/friend/group cards, detail screens, previews, notifications and exports. Batch settlement requires one known currency. Individual unknown/foreign expense settlement may mark its shares without claiming a denomination or combining amounts.
- **Financial capability boundary:** add optional `required_financial_contract` to accounts and capability 2 to all financial query/write/import boundaries. Before a newly currency-aware expense or V3 identity-equivalent multirow history becomes visible, atomically raise every affected viewer's floor to 2; the floor never downgrades. Current readers/writers send capability 2; a missing/lower capability at a fenced account receives actionable upgrade-required before any complete or partial financial snapshot or write. During a pending V3 alias operation, financial read preflight also checks candidate records against source/target operation-member markers before returning a page; this closes the window before a worker raises a foreign viewer’s account floor. Completed markers retain the minimum contract requirement. A higher-capability client may read unaffected complete data, but affected actor/creator snapshot channels remain pending until completion. Preserve old argument/return contracts for unfenced legacy records where safe, except insecure new authoring without denomination is rejected. Query fallback must not treat capability/pending errors as endpoint absence. This deliberate old-client upgrade requirement belongs in rollout and PR cases; optional fields alone are not considered compatibility proof.

### 5. Actor fencing and acknowledged lifecycle results (F08–F09, F17–F19)

- Make reconciliation always capture account ID/data epoch and check after each await. Friend-sync and bulk-import chunks carry expected actor to server validation and stop on cancellation/session changes. Mocks must model current-auth behavior rather than mask races with input email partitioning.
- Persist suppression by `(account identity, stable expense client ID)` for every shared record detached by Clear All. That explicit record suppression wins over all later settlement, migration, link/relink and job retries; updated_at or a new link never clears it. Use the clear operation cutoff only to define its bounded batch membership, not as an expiry. A later link may reveal previously unseen historical records with no suppression, but cannot reveal a record this account actually cleared. New expense IDs remain visible normally. Only an explicit authorized restore/unhide operation may clear suppression, if such UI is added; ordinary import does not silently unhide. Preserve other viewers' history.
- Linked-friend deletion handles current server state atomically or returns an enforced typed failure. iOS only retains deletion tombstones after acknowledged success.
- Replace scans of all unrelated owner expenses during friend deletion with targeted indexes and bounded resumable work; test unused-friend deletion after 513 unrelated expenses.

### 6. Concrete bounded identity/reference protocol (F05, F16)

- Add `member_references`, unique by `(entity_kind, entity_document_id, normalized raw member_id)`, indexed by member/kind, entity, and owner/member/kind. Cover group members and expense payer/involved/split/participant/inactive IDs. Each row carries the authoritative owner account and current source revision/generation. Presence finds candidates only; reread and authorize the source record before any visibility update.
- Group/expense canonical insert, patch and delete helpers maintain references in the same transaction, including import, cleanup, maintenance and migration routes. An internal resumable backfill pages current source tables, rereads live documents, replaces reference sets, removes deleted stale candidates and stores phase/cursor. New jobs require its separate completeness marker. Existing production markers are never changed by tests or this PR.
- New V3 claim/accept/local-merge endpoints return a stable authenticated operation with immutable source closure, target identity, bound token/request/friend, explicit selected local friend, actor/creator accounts, generation, scan cutoff, phase, member index/entity cursor, attempts/error and completion. Use **consent/alias commit → reconcile groups → reconcile expenses → complete**. Install identity/provenance/friend canonicality and a durable operation atomically; do not stage destructive financial rewrites. Global claims establish only the explicitly consented placeholder alias. Owner-local merges store closure only on that owner's target friend, delete the duplicate relationship atomically, and never touch global account aliases or other owners' financial data.
- Authoritative owner-local equivalence is shared across owner selectors, direct-ledger lookup, participant authorization, cleanup and owned-expense visibility resolution. A local alias grants no access to foreign-owned financial history and creates no global friendship. New writes resolve current equivalence synchronously and maintain references/visibility in the same transaction.
- Workers paginate reference candidates in small byte/row/write-bounded batches using source IDs plus cutoff. They reread current documents, revalidate live alias/friend provenance, inactive IDs, suppression, deletion fences and generation, then use canonical visibility/revision helpers. Foreign records may receive only derived visibility/revision changes, never payer, split, amount, flags, name or ownership rewrites. Post-cutoff writes are already synchronous and do not extend the drain indefinitely; removed/replaced references are harmless on reread.
- Operation generation and source/target provenance are checked on every batch. Revoked consent cancels grants and schedules/remains responsible for removal of previously materialized access. Account deletion takes precedence and fences the job. Transient failures persist retry state and bounded backoff; terminal errors keep affected clients in an explicit recoverable processing/error state rather than falsely complete. Same operation/selection retries resume the same cursor; changed selection conflicts. Final completion commits phase, durable token/request completion and relevant revision bumps together.
- Affected actor/creator financial and group sync channels check pending operations **before** returning a snapshot. Current V3 clients preserve last complete state and show processing; no partial snapshot replaces it. Status/resume endpoints work after relaunch and are active-account/owner authorized. Visibility rows remain candidates: read-time authorization rechecks live identity, inactive state and suppression so a stale row cannot outlive revocation.
- Legacy synchronous endpoints retain atomic small-case behavior, now including all affected foreign visibility. Full bounded preflight occurs before mutation. If work cannot be represented atomically, fail upgrade-required before any writes. An old request encountering a pending V3 operation never reports completed legacy success. Current client uses V3 for all long-history operations; no constant-only workaround or unbounded scan.
- Charge actual indexed identity work under existing hard budgets, not 80 hypothetical lookups for every member. V3 local alias-only merging makes a 65-expense or 12-person history finite materialization work without rewriting its money.
- Required gates: 65+ expenses and unrelated large owner history; 12-person and dense aliases; same/different retry selection; crash after alias commit; process relaunch; writes before/after cutoff; deleted source; owner conflict/change; suppression/revocation/account deletion during every phase; foreign financial data byte-for-byte unchanged; no stale candidate access.

### 7. Lossless backup and release readiness (F11–F13, F25)

- Version portable export and reject unsupported versions explicitly while preserving legacy reads. Parse logical quoted CSV records across newlines. Use round-trip-safe numeric text, not two-decimal formatting; export all zero/tiny splits and subexpenses with stable IDs/flags. Eliminate nameToExistingId auto-matching for both explicit friends and group members: map each source UUID independently, preserving that UUID or a distinct per-source replacement. Preserve UUIDs, contextKind, notes, currency absence and settlement rows; never fabricate missing liability. Grouped-individual import has no fake group requirement. Only explicit friend records create confirmed friends. Production/CI paths share transformations; tests trace actual exporter → parser → production payload → backend stored records. Legacy omitted information is reported unrecoverable, not called lossless.
- Configure Clerk key/issuer by build/deployment environment using project.yml and backend env configuration. Add validation that rejects mismatched production/development settings at release readiness rather than silently switching existing users. Retain documented development setup. No credentials in commits. Provide an operator runbook for production Clerk setup and verified account continuity; use environment-specific associated domains as well as key/issuer/Convex settings. Missing/mismatched Release configuration blocks release readiness rather than making an accidental live identity switch. Validate the full Debug/Internal/Release matrix in tests/build checks. Unknown live credentials and account continuity remain explicit operational prerequisites, not fabricated values.
