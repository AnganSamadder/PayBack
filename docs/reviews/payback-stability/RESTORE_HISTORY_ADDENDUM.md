# Historical restore contract addendum

Status: design candidate v3; frozen for three independent Sol reviews before production changes.
Revises v2 (`066b804bac65f3962b54d5aa84915acc1abfa9425b6f057d5a6a1d474a694797`); v1/v2 remain immutable. V3 retains v2's stewardship and adaptive transport rules and adds source-verified inactive-party handling, direct-history consent, precise protocol errors, and neutral-session recovery.

Scope: repair the proven canonical-expense/raw-group restore failure and the 64-member export boundary without expanding group membership limits or importing identity authority.

## Decision and boundary

Keep the current group roster unchanged and bounded to 64 members. Remove portable roster expansion. Keep every expense's original group/context, payer, participant IDs and names, split IDs, amounts, currency, subexpenses, notes, and settlement flags. Existing financial validation and per-expense participant limits remain unchanged.

An authenticated owner may restore a historical financial row into their own group even when a participant is absent from its current roster, provided that exact row declares the historical identities in the same import request. **Storing that owner's private history does not authorize sharing it with the account named by a raw ID.** Every raw financial participant of every newly restored GROUP/DIRECT expense remains subject to a persisted sharing restriction, including participants currently in the group. This is a deliberate restored-history privacy rule, not selective compatibility: later membership or identity removal can withdraw sharing while the owner's data stays intact. Grouped-individual history retains its existing rules. The manifest cannot create group membership, a friendship, a global/local alias, a direct-ledger pair, or a trusted linked-account field.

This replaces both rejected alternatives: a 128-member roster is not closed under repeated linking/export cycles; a permanent group-wide restore exemption would authorize unrelated later rows. No durable restore operation or transferable restore token is introduced.

## Wire contract and exact binding

Add optional `history_manifest` to `bulkImport` alongside its existing actor/capability arguments:

```ts
history_manifest?: Array<{
  expense_id: string;
  group_id: string;
  historical_member_ids: string[];
}>;
```

Each entry binds only to one expense in this invocation's `expenses` array. IDs use the existing member-UUID normalization rules; expense/group client IDs keep their existing identifier rules.

Perform complete **chunk-level manifest preflight before any friend, group, expense, reference, floor, visibility, or revision write**. This covers all entries in that request, including entries bound to already-owned expense IDs that will later be skipped. A malformed manifest throws and rolls back the whole chunk; it is never a per-row partial-success error. Previously completed chunks remain committed and must still appear in an incomplete progress result. Preflight validates:

1. The authenticated actor matches `expected_account_id`/email and passes capability, pending-identity, and deletion fences. A manifest requires financial capability 2.
2. Expense IDs, manifest expense IDs, and each manifest's normalized member IDs are unique. Reject dangling entries, repeated entries, group-ID mismatches, empty declarations, and declarations that differ from that expense's complete validated raw financial participant set. The declared set must equal the normalized union of payer/involved/split IDs; validated participant ID/object sets must already agree with it.
3. Every referenced group is either created by this request for the actor or already consistently owned by the actor. Caller visibility alone is insufficient. Reject foreign ownership, conflicting owner tuples, deleting groups, and pending group-history reconciliation. Incoming group records never update an existing group's roster or ownership.
4. Validate the historical money and matching payer/involved/split/participant sets before applying the exception. A manifest cannot repair mismatched sets or authorize fabricated/coalesced financial rows.
5. Compute the expense participants authorized by the live stored group owner's identity scope, as in the repaired ordinary restore path. With a valid complete declaration, an outside participant may be stored as private history, subject to the persisted rule below. Without a declaration, every participant must pass the existing live membership check. A declaration cannot expand active sharing.

No manifest means the existing live-owner-equivalence membership rule applies. A successful group-backed restore still stores the full participant restriction server-side; no-manifest compatibility does not bypass the restored-history privacy rule. The manifest is required only to authorize private storage of outside-context historical rows. A grouped-individual expense remains on its existing group-free restore path; reject a manifest for it. This addendum does not relax its confirmed-participant rules.

A later request has no permission inherited from an earlier manifest. It must bind its own declaration to its own newly restored rows. This is safe without a durable restore table because the exception only permits private storage of a precisely declared row, not access to another account or a current group-member capability. Persisted per-expense restrictions, rather than a reusable group exemption, enforce that distinction after the request ends.

## Persisted restriction and sharing authority

Add optional server-owned fields to expenses:

```ts
restored_historical_member_ids?: string[];
restored_history_context_member_ids?: string[];
has_restored_history?: true;
```

Only validated bulk import can introduce these fields. Store the full normalized raw financial participant set for every newly restored GROUP/DIRECT expense, with or without a manifest. Ordinary authoring, metadata updates, settlement, legacy writers, retries, and client DTOs cannot introduce, replace, or clear it. The server also captures the actual stored group's original raw member IDs in `restored_history_context_member_ids` (at most 64); the client does not supply these as alias assertions. They are dependency metadata only, not payer/split/participant/viewer identities. `has_restored_history: true` is an index discriminator, not authorization. Absence retains existing document behavior.

Member references for a restricted expense include its original financial IDs plus these context dependency IDs. This lets an accepted link of current raw context X discover historical canonical B rows even when X does not occur in their financial fields. Context references must never enter financial math, participant arrays, viewer enumeration, self classification, or destructive cleanup's financial-participant matching. Existing reference bounds (1024/entity) cover at most 129 distinct financial/context IDs; their actual read/write cost remains charged.

For each declared ID, decide active sharing from current server truth:

- Derive that financial ID in the **expense owner's** live identity scope.
- Derive current group-member IDs in the **group owner's** live identity scope.
- Allow that historical identity to contribute a viewer or participant mutation authority only when those derived identities match. Direct canonical IDs alone, imported linked metadata, names, a manifest, and a manual friendship do not satisfy this test.
- Inactive identities, deleting/deleted accounts, pending identity generations, and account/expense-client-ID suppression still exclude access. The authenticated expense owner always retains their own private history, subject to account deletion and their own clear/delete actions.

For **restricted restored direct history**, also require the live financial identity set and the live direct-roster identity set to equal the same exactly-two-person pair: the stored expense owner and the proposed registered viewer. Use expense-owner scope for the financial set and group-owner scope for the roster. The expense owner must currently have an eligible confirmed `account_friends` record whose server-proven link resolves to that exact active viewer. Imported manual friends, imported linked fields, a direct flag, a roster entry, and an existing pair-mapping row are not consent evidence. Compute this predicate read-only; do not call the ledger resolver that writes pair mappings. No reciprocal/mutual friendship requirement is added. Ordinary non-restored existing direct history and owner metadata/settlement rights keep their existing behavior. If the gate fails, the owner retains private history.

Owner-side friend removal, status downgrade, unlinking, and friends-clear change this direct-history predicate. They must reconcile affected restricted direct expenses and force prior/current viewer revisions using indexed financial/member references and confirmed owner scope; do not scan unrelated history. Read-time access and non-owner mutations apply the new predicate immediately. This is not a new eligibility condition for ordinary retained direct history.

An accepted link that makes current group placeholder X equivalent to historical B can therefore activate B. A participant genuinely removed from the current group needs an authorized membership change; adding a friend alone does not reshare removed group history. If expense and group ownership later differ, their local alias scopes remain separate: a foreign owner's local alias cannot silently redefine the expense's financial identity. Global equivalence or independently consistent owner scopes can still establish the match.

Apply this rule to all visibility reconciliation, public reads before filtering, settlement, and non-owner metadata/delete authorization. Hidden historical payer IDs must not retain a delete or settlement side channel. The response financial map remains derived advice, never write authority; it preserves the expense-owner scope and original rows. Owners may still view amounts assigned to a historical person who currently receives no shared expense.

The canonical write helper must enforce this filter even when an import/legacy caller supplies explicit viewer IDs. Final durable suppression filtering runs after all candidate eligibility checks. Neither membership changes nor relinking remove suppression records.

### Deleted/deleting third parties: restore storage, never active identity

Source verification: `bulkImport.resolveImportIdentity` currently throws on a deleting/deleted account only while resolving incoming **friend headers**; it is not called for financial rows. `resolveServerProvenLinkedAccount` can throw for a deleting existing friend account (`resolveProvenFriendLink` already excludes deleted accounts). Fresh group insertion separately rejects fenced members through `scrubInactiveAccountMembers`. Thus deleting a nonexistent `resolveTarget` check or weakening the actor guard would be both inaccurate and insufficient.

Keep authenticated actor, expected-actor, actor/group-owner deletion, and pending-identity fences unchanged. Normal group authoring, friendship authoring, linking, and ordinary expense authoring keep their current inactive-account rejection. Add narrowly named internal restore preparation that reads third-party status atomically and distinguishes active trusted identity from inert history:

- A deleted/deleting third party never supplies canonical link provenance, viewer eligibility, active friendship, or a direct-sharing/pair proof. Existing owner-friend provenance resolution treats that third party as non-granting rather than aborting unrelated historical storage. Only explicit incoming header rows receive restore changes; do not rewrite unrelated relationships merely because import examined them.
- An incoming friend header resolving to a fenced third party is restored only as a server-sanitized ghost/unlinked record with the original raw member ID; strip linked IDs/emails, profile/contact fields, nickname, and active/manual/friend status. Keep its normal per-item created/updated/already-present outcome and attach the explicit `notice: "inactive_party_scrubbed"`; group/expense outcomes with authoritative omission/scrubbing use the same optional notice, and the import UI reports that sanitization without calling the item rejected or inventing another terminal status. This exception cannot overwrite a different live proven identity or trust a client-supplied ghost assertion as deletion truth.
- For a **new restored group**, omit server-proven fenced third-party IDs from the active roster before inserting it; retain active members and the original group ID/name/direct flag. Existing groups remain immutable through import. This follows deletion's removal semantics and avoids a new inactive-group-membership protocol. The omitted historical IDs remain in the original expense financial rows; they are not remapped or dropped from money-bearing records.
- Preserve expense payer/involved/split IDs, split IDs, amounts, currency, and settlement flags. Apply the existing authoritative deletion scrub to the fenced participant's display/link metadata and add its original financial ID to `inactive_participant_member_ids`. Such IDs cannot regain visibility, mutation rights, or stewardship through a later alias claim or roster change. For source-proven aliases to the same fenced account, apply the same policy; a stale/unproven alias does not let the client mark another live account inactive.

This exception is limited to server-authoritative account deletion, never ordinary unlinking, loss of friendship, or a client assertion that someone is gone. A restored direct ledger with only one surviving active member remains private historical infrastructure under its original direct flag; it cannot establish an eligible pair or authorize new direct authoring. This is an explicit exception to display-name and current-roster preservation for an authoritatively deleted/deleting person: privacy scrubbing wins; the backup cannot restore deleted profile identity into active/shared state. It is not an exception to financial-row preservation. Import must perform the scrub itself in its transaction, including when the account's deletion job already passed its friend/group/expense phase; do not assume a later cleanup page will revisit newly inserted records. An unknown/unregistered offline ID is not evidence of deletion and remains governed by ordinary manual-identity rules.

## Reconciliation and snapshot generations

Do not scan unrelated account history. Reuse `member_references` for accepted global/local linking and the existing indexed owner-local dependencies. Declared historical IDs and the server-captured original context dependency IDs remain in the expense references. Link workers reconcile affected expenses with `forceRevision: true`, including owners and viewers whose membership did not change. Existing raw-member, local-target, and owner pending barriers block snapshots until the relevant operation completes.

Group membership can change eligibility without a link operation. Add a bounded group-history reconciliation path:

- Index declared-history expenses by `group_ref` plus a server-maintained `has_restored_history` boolean, set and preserved with the declaration. The boolean is an index discriminator, not authorization.
- A successful membership change checks that index and atomically starts a new generation when affected history exists. Use `group_history_reconciliations` records with `group_ref`, `owner_id`, `generation`, optional `cursor`, `phase: pending | failed | complete`, `attempts`, optional `error`, and timestamps; index by group/phase and by owner/phase for bounded discovery. Store the active job ID on the group. This is reconciliation state, not a restore grant. Schedule the first page in the same transaction. Only one active job is allowed per group; completion clears its pointer atomically with the final revision bump.
- Process one indexed page at a time, starting at most 8 expenses. Prepare the whole page through canonical visibility/reference/revision preflight before applying any writes. A typed deterministic budget rejection reduces the page 8→4→2→1 at the same saved cursor and generation; only the successful prefix advances the cursor. Each size attempt runs in its own internal mutation transaction. The scheduled orchestrator catches only the typed rolled-back budget error and requests a smaller page at the unchanged cursor/generation in a new transaction. Never reset counters and retry inside the same transaction: reads already performed still count against Convex limits. Persist only the next requested size between failed attempts, never a partial financial result. A supported single expense must fit verified worst-case limits; otherwise leave an explicit failed maintenance state, never loop or skip it. Use forced prior/current-viewer revisions. Retried pages are idempotent; stale generations cannot publish completion.
- Fence reads and participant mutations for affected group history before authorization/filtering while its generation is pending or failed. Serialize further group membership changes against that generation; metadata-only group edits may proceed without changing its membership snapshot. Reject imports/authoring into the pending group with a recoverable reconciliation error.
- Bump group revision when scheduling and when completing so clients retry the authoritative snapshot. The expense worker bumps all affected expense-viewer revisions, including after a retry of a page whose prior acknowledgement was uncertain. A continuation from before the change must fail its expected-revision check after completion, including when access remained unchanged.
- Group deletion/account cleanup cancels or supersedes the job and removes its records through the existing bounded lifecycle. Workers recheck group existence/deletion/ownership generation before writes. A failed job remains fenced and retryable; do not publish partially reconciled pages.

Current-group relinking can affect a historical canonical B even when the financial rows reference B but not group placeholder X. The captured context member references cover original X. Acceptance workers must include both source and target identities and their owner-local dependent references, then run the same sharing filter. Every changed group discovered by either the main identity pass or owner-local dependent pass must also drain its indexed restricted-history expenses across all expense owners, including context added after the restore snapshot. Keep this work inside the existing identity operation: persist a bounded group-history subcursor and the return position, drain it using the reusable prepared page routine, and only then advance that group reference. Do not fire-and-forget a child group job and retire identity markers early. Source AND target identities and their proven live equivalent/dependent identities participate in discovery. Legacy synchronous identity paths must prepare the same bounded work or reject with the existing upgrade-required path before committing; no legacy bypass. Tests must prove actual discovery for original context, later-added context, different expense/group owners, loss of old eligibility, and gain of new eligibility.

The canonical worker uses an internal generation-verified eligibility mode for the exact operation it is reconciling, so its own pending marker cannot deadlock its projection. It must retain provenance, deletion, suppression, and unrelated-operation fences; never pass a public/global `allowPending` switch. Overlapping operations on the same context must serialize or share verified generation progress without cyclic waits, and keep public context reads fenced until all relevant work finishes. Imports and roster additions check readiness of current raw group identities and owner scope, not just financial IDs, preventing post-cutoff records from being missed.

### Failed-job discovery and recovery

Provide `groupHistory.pending` (paginated owner jobs), `groupHistory.status(job_id, visible_expense_id?)`, and `groupHistory.resume(job_id, visible_expense_id?, expected_account_id, financial_contract_version)` as purpose-built endpoints. They authenticate an active account, check the expected actor/capability on mutation, and validate the actual job/group generation and ownership. They bypass only this job's public snapshot-pending barrier; they cannot bypass deletion, account identity, or foreign ownership authorization. Status exposes only group/job IDs already authorized to the caller, phase, retryability, and a safe error code, never hidden financial participants or rows.

The source group owner can discover and retry their own jobs without first fetching the blocked group/expense snapshot. A foreign reader can query status or request rescheduling only when they have an existing unsuppressed financial visibility row attached to the affected group, or an existing current authorized group-visibility relationship; guessed historical IDs do not suffice. For financial-viewer authorization, the optional expense client ID is only a lookup hint: verify the stored expense belongs to this group, then verify its account/expense visibility row and durable suppression with indexed reads. For group-reader authorization, verify live current membership independently of any stale fanout row. Use a private read-only eligibility resolver that bypasses only this job's snapshot barrier, not provenance or deletion rules. Do not trust a client-supplied ownership field or invoke the blocked public snapshot helper. Pending read errors expose a job ID only after this limited relationship check; unauthorized callers get a generic error. Paginated owner discovery uses the owner/phase index, not an expense scan. Foreign rescheduling never changes source owner, generation, membership, cursor, or job scope. A rate-limited idempotent resume schedules the exact existing job once, preserving its last committed cursor; complete/stale jobs return their terminal status. Ownership change/deletion supersedes or cancels the job under the internal lifecycle instead of allowing a reader to adopt it.

Use bounded automatic retries for transient failures, then a durable `failed` state with explicit `retryable` versus `maintenance_required` classification. A budget failure above one item reduces page size; it is not a terminal failure. An unsupported single item or invalid source invariant is maintenance-required, with no automatic retry loop. A maintenance error must identify the safe error code and affected already-authorized group, retain progress, and expose the existing administrator/internal repair route; resuming unchanged invalid data must not be advertised as a guaranteed fix. Auth/account hydration and job discovery do not depend on successful financial snapshots: the client retains the authenticated actor behind a neutral data-recovery gate during cold sign-in, resolves/resumes pending history before full hydration, and does not enter normal RootView tabs with empty/partial arrays. In an already hydrated session, preserve the last complete arrays and present a visible retry/recovery surface. Use typed `RemoteLoadOutcome`/history-recovery state: current `loadRemoteData` returns void and swallows errors, so it cannot prove refresh success. Resume/status run without the blocked snapshot; after completion retry actor-bound full hydration, not `checkSession` (which resets arrays). It does not turn this into a failed-login or endless fetch retry cycle. Foreign readers stay fenced before filtering until completion; retry is not permission to display partially reconciled data. Final revision changes trigger normal authoritative refresh.

## Export, chunks, retries, and compatibility

No new CSV section is required. Preserve the original group/member section. For every GROUP/DIRECT expense in a network chunk, the production request builder declares its complete raw financial participant set, even when all participants currently belong to the exported group. Emit exactly one manifest entry per such expense. Grouped-individual expenses emit none. Compute declarations after the existing explicit ID remapping step, from payer/involved/split IDs only; descriptive-name keys are never financial participants. A missing source group is an explicit conversion error, not an empty roster to infer against. It retains the complete parsed group metadata while converting later chunks, even though those chunks omit already-sent group writes. Reconstructing a later `BulkImportRequest` must copy that chunk's `history_manifest`, and the real Convex adapter forwards it unchanged. No derived identity maps or trusted links are exported. Repeated export/clear/restore keeps the roster at 64 and keeps all raw financial identities; it cannot accumulate canonical roster additions.

When restoring into an existing owned group whose live membership changed since export, a valid complete declaration preserves the row privately; current eligibility alone controls sharing. An old/no-manifest request with an outsider still receives an explicit row error. Import never changes the existing group to make a row fit. Since every backed restore stores the same complete restriction, later membership changes and repeated export/clear/restore cannot accidentally remove a previous restriction.

Idempotent retries of an already-owned expense do not overwrite financial fields, declarations, or visibility. Reject duplicate IDs within a chunk. A foreign-owned expense ID aborts the transaction as today. A new payload reusing an existing owned ID is reported as already present, not as an applied edit; no manifest can alter that existing row. Actor/session changes stop subsequent chunks, and cancellation does not turn a partial restore into reported complete success.

Old clients omit the new argument and retain ordinary safe membership validation. New clients send the optional manifest to the updated backend; validator errors must not trigger fallback that drops it. Any stored declaration raises the existing financial capability floor for owner and eligible viewers, including nil-currency history. New fields are optional for existing documents. Responses need not expose the server-owned restriction because the backup builder reconstructs complete declarations from original financial rows; DTO decoders tolerate the additive fields.

Direct history keeps its original `is_direct` group flag and original raw roster. A manifest is never evidence of friendship or a two-person pair. New direct authoring still requires a confirmed friend and exactly two live equivalent people. Reuse after relinking follows the existing canonical-pair resolver; restore itself neither creates nor rewrites pair mappings.

### Bounded phased transport and exact outcomes

Replace the current fixed-100 expense loop and all-header first request with serial **friends → groups → expenses** phases. Keep the complete immutable parsed/remapped source available throughout. Each phase starts with at most 16 friends, 4 groups, or 8 expenses per request; these are initial maxima, not promises that every aggregate fits. A header-only backup uses the same bounded friend/group phases. Expense requests have no repeated header writes and contain the exact manifests for only those expense rows. Never split an individual group, friend, expense, manifest, financial set, or split row to fit.

The server exposes a typed `ConvexError` payload `{code: "IMPORT_BUDGET_EXCEEDED", scope: "request" | "identity" | "group" | "expense" | "references" | "revisions"}` only for its measured deterministic aggregate budgets. This error is thrown from the complete mutation so Convex rolls back **all** writes, including any earlier header writes in that request; it is never caught into row-level `errors` or returned with success/counts. Prefer complete prepared preflight before application. Identity/account/group validation errors, money errors, capability or pending-state errors, and platform/transport errors never masquerade as this code. Instrument all measured preparation, including metadata/reference/floor/revision work; preserve the original budget error class through helper layers. A generic timeout or lost response does not establish rollback. The pinned ConvexSwift 0.7 `ClientError.ConvexError(data: String)` retains the structured JSON payload: decode its exact code/scope into a typed import-budget error in `ConvexAccountService` **before** the current `PayBackError.underlying` wrapping. Never classify by substring. `ClientError.InternalError`/transport failures are uncertain outcomes; `ServerError` and other structured Convex validation/auth errors stop unless they are the exact documented recovery code.

On this exact typed rollback error, bisect that phase's queued items in stable order and try each half. Preserve every client ID, row value, manifest, expected actor, and source metadata; do not rerun name matching/remapping or regenerate IDs. A one-item rejection stops with an explicit incomplete result and the failed item/phase. The server must test that each supported maximum-size single item fits with existing supported account context; deterministic aggregate rejection must always have a finite fitting path for healthy backups. Header phases must also subdivide, so 24 fresh 64-member groups do not remain in one permanently failing request.

For an uncertain transport outcome, retry the **same** request and IDs a bounded number of times (at most 3), with cancellable backoff. Do not bisect until a subsequent definite budget rejection proves that attempt rolled back. Existing-row immutability makes same-ID replay safe. Stop immediately on actor/epoch change or cancellation before/after every call and delay, and before advancing phase or publishing the final snapshot. Progress belongs to the captured actor/operation and cannot publish into the next session. A deterministic validation/auth/capability failure is not retried as a smaller request. A row-level validation error may report partial committed rows as today, but stops further phases/queued work with an incomplete result; it is never labeled complete success.

Add optional per-item outcomes to the import response: `{kind: friend | group | expense, id, status: created | updated | already_present | rejected}` plus safe error codes for rejected items. Preserve existing aggregate `created/errors` fields for compatibility, but the new importer derives progress from one terminal outcome per `(kind,id)` and never sums retry acknowledgements. Every outcome ID identifies the stable normalized **request/source** item, never a server-canonical replacement chosen during alias resolution. Friends use that source identity selected before transport; no retry invents another ID. Exact coverage compares those request IDs, even when several source identities resolve to an existing stored row. On an uncertain committed response followed by `already_present`, count that item as **present/processed**, not as provably newly created. Without durable receipts the client cannot reconstruct the lost attempt's exact creation count; show confirmed created/updated counts separately from already-present/uncertain-origin counts. This is an explicit truthful limitation, not a reason to add restore grants or claim an exact added count. Extend `ImportSummary` with defaulted processed/already-present/updated and incomplete phase/error fields; remove the UI claim that zero newly-added items means nothing was restored. Optional outcomes remain decodable for compatibility, but the modern importer requires exact unique coverage of all request items before treating them as terminal; absent/malformed outcomes produce an explicit incomplete response, not synthesized success from aggregate counts.

Completion requires all three queues to finish, every input item to have a non-rejected terminal outcome, and an explicit successful actor/generation-bound authoritative refresh result. `AppStore.loadRemoteData` currently catches failures and returns void; the state owner must expose a real success/incomplete result for this integration. Preserve and display processed counts and the remaining/failed phase on cancellation, account switch, row errors, unsupported single items, or exhausted transport retries. Already committed earlier requests stay committed; no success message suggests an atomic whole-backup rollback. Snapshot refresh failure reports data committed but refresh incomplete, and never publishes partial local arrays or data into a new session.

## Bounds, cleanup, and implementation owners

Use the existing 512-expense request ceiling and 65-identity expense ceiling. Manifest entries cannot outnumber request expenses; each declaration cannot exceed its expense's validated unique financial set. Reject over-budget payloads before writes. Subdivision must reduce actual work: replace complete-owner group/expense/friend preloads on this path with bounded indexed lookups for the current request's IDs and proven identity dependencies. Do not make a one-item request rescan all previously restored headers or unrelated account history. Required migration/readiness failures remain explicit maintenance errors, not budget errors to bisect indefinitely. Count manifest bytes, group reads, live identity/eligibility queries, reconciliation lookups, reference writes, capability floors, fanout writes, and revision writes in the existing aggregate import/preflight budgets. Cache group/owner identity work across the chunk; do not add an unaccounted full group or friend scan. Group roster/viewer bounds remain 64/65; per-expense viewer bounds stay unchanged.

Deleting an expense deletes its restrictions with the record and removes member references normally. Clear-all suppression remains keyed to the original expense client ID. Account deletion preserves the distinction between financial references and dependency-only context references: use references to discover candidates, then confirm an actual financial identity before destructive participant cleanup. Restrictions confer no extra identities and cannot suppress required privacy scrubbing. Ownership transfer follows the pre-transfer stewardship rule below; recomputing only after transfer is insufficient. Add indexed job cleanup to account/group deletion; no new 128-member cleanup allowance is needed.

### Stewardship must not promote private history

For every automatic ownership-transfer path, a restricted expense may transfer only to an active, non-deleting, unsuppressed **financial participant already eligible to view that expense under its old owner and current group scopes before transfer**. Evaluate that predicate while retaining the original owner tuple. Do not first make a candidate owner and then invoke the owner-access exception. Raw canonical IDs, historical declarations, group-only membership, dependency-only references, client linked metadata, and stale `user_expenses` rows are not eligibility evidence by themselves. Recompute live sharing plus suppression from server truth; the candidate must also occur in actual financial rows.

Deletion's internal preparation may bypass the public pending gate only to evaluate the deleting account's unchanged pre-transfer scope; it must still exclude deleting/deleted candidates, preserve identity provenance/deletion fences, and apply suppression. Stage restricted-expense steward decisions before changing their source group ownership, or persist the verified original-scope decision in the same bounded cleanup generation. A separate group transfer to a group-only participant cannot make that participant an expense steward. If no eligible successor remains, use the existing no-steward expense deletion outcome. Do not preserve private history by assigning it to a hidden participant. Privacy scrubbing remains mandatory whether a steward is selected or not.

For an eligible transfer, retain restrictions/context dependency metadata, write the new owner tuple only after selection, and recompute resulting viewers with final suppression filtering. Clear/revoke departed-account access and bump affected revisions atomically. Revalidate the candidate immediately before the transfer transaction so a claim, suppression, or deletion change between pages cannot turn an old prepared choice into authority. Context-only reference candidates must be confirmed against financial surfaces before any destructive cleanup action.

## V3 triage decision log

- **Accepted, source-verified:** inactive third parties can currently abort friend/group header phases and unrelated friend-provenance preparation. Repair with explicit restore-only inert storage and cleanup-equivalent scrubbing, not weaker actor or active-authoring guards. There is no current `resolveTarget` function; the verified paths are named above.
- **Accepted with scope correction:** restricted restored direct sharing needs the owner's current confirmed, server-proven relationship and the same exact canonical pair. **Rejected:** mutual friendship would invent an unsupported product requirement.
- **Retained context references:** removing them is an optional optimization, not a correctness prerequisite. V2 adaptive budgets provide a finite path; removing them now requires broader parent/child dependency discovery and cleanup changes. Keep dependency-only context IDs, plus mandatory changed-group drain inside the existing identity operation. No new parent-child restore architecture is introduced.
- **Strengthened:** manifest validation is whole-chunk atomic before any writes. Earlier successful chunks remain visible in truthful partial progress. The storage exception never grants sharing.
- **Rejected:** automatically releasing failed-job fences would publish inconsistent visibility and mixed financial generations. Retain the fence, neutral recovery/status/resume, bounded backoff, adaptive prepared pages, and explicit maintenance state. No login failure loop and no empty authenticated financial tabs.
- **Accepted installed-SDK details:** typed ConvexSwift budget decoding, exact per-item response coverage, truthful summary UI, and a real hydration outcome are required integration work. For workers, prefer the existing internal action → step mutation → failure-recording mutation pattern. Each failed step transaction rolls back page writes/cursor/revisions; direct helper calls plus catch do not. Nested mutation rollback exists but shares transaction resource consumption, so it does not guarantee enough budget remains to record recovery.
